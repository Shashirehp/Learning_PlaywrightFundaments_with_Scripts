Test automation / architecture notes

How Playwright talks to a browser

A walkthrough of the client, server, and protocol layers behind every page.click() — from your test script down to the browser engine and back.

The four layers

A Playwright test never talks to the browser directly. Every command passes through a small chain of translation before it reaches Chromium, Firefox, or WebKit.

Client

Your test script. It calls Playwright's API bindings — the same call, page.goto(), works whether you write Java, Python, or JS.

WebSocket

A persistent, bidirectional connection between client and server. The initial handshake is HTTP, then it upgrades — faster than a new request per command.

Playwright server

A Node.js process that starts automatically. It receives commands and translates them into browser-native instructions — you never manage it directly.

CDP+

Playwright's extension of Chrome DevTools Protocol. It adds tracing, HAR recording, and multi-context support on top of vanilla CDP.

What happens on a click

Tracing a single test line — page.goto("https://example.com") followed by page.click("button#login") — through the stack:

  1. Client sends the commandThe test script issues goto() and click(). These get serialized and sent over the open WebSocket.
  2. Server parses and translatesThe Playwright server reads the command and converts it into browser-native instructions — CDP commands, for Chromium.
  3. Browser executesThe browser navigates, waits for the page to be ready, locates button#login, and dispatches a click through its own automation API.
  4. Events flow backThe browser reports status — Page.loadEventFired, click confirmation — back through the server and over the WebSocket to the client.
  5. Test continuesYour script proceeds to the next line — an assertion, a log, or the next action — now that the result is known.

Starting the server without starting it

In a Java project, calling Playwright.create() quietly launches the Node.js server as a background process. Your Java client then talks to it over the same WebSocket channel described above.

// Java client — the server starts and stops for you
Playwright playwright = Playwright.create();
Browser browser = playwright.chromium().launch();
Page page = browser.newPage();
page.navigate("https://example.com");
page.click("text=Login");
// playwright.close() shuts the server process down

No manual startup, no manual teardown. The Java binding owns the Node.js process for the life of that Playwright object.

Common questions

Is CDP only for Chrome?

Yes — CDP itself is specific to Chromium-based browsers. For Firefox and WebKit, the Playwright server talks to each engine's own native protocol instead. CDP+ is the abstraction that makes all three look the same from the client's side.

Why WebSockets instead of HTTP requests?

A WebSocket stays open for the life of the session. Commands and events travel over one persistent connection rather than opening a new request each time, which cuts latency significantly for the volume of calls a browser session makes.

What do browser contexts add?

A context is an isolated environment inside one browser instance — its own cookies, storage, and permissions. It's what lets Playwright run tests in parallel without one test's session leaking into another's.

Interview note

The CDP-vs-CDP+ distinction is a common probe point: CDP is Chromium-only and predates Playwright; CDP+ is Playwright's own cross-browser layer built on top of it, which is why the same API call works identically across all three engines.
